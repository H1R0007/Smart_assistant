# Руководство разработчика (Contributor's Guide)

Голосовой ассистент построен на модульной, плагинной архитектуре. Ядро управляет жизненным циклом и устройствами ввода/вывода, а весь функционал реализован в виде независимых команд-плагинов.

## 1. Архитектура в одном абзаце

Ассистент состоит из **ядра** (`core/`) и **команд-плагинов** (`commands/`). 
Жизненный цикл: `Listener` ждёт wake word → `Recognizer` транскрибирует речь (Whisper) → `CommandRouter` ищет подходящую команду → команда выполняется и отвечает через `Speaker` (TTS). 
Команды получают доступ к ядру через `AssistantContext` — строгий контейнер зависимостей. Все интеграции с внешними сервисами вынесены в `core/integrations/`.

## 2. Как добавить новую простую команду

Каждая команда — это класс, унаследованный от `BaseCommand`, лежащий в любом файле внутри папки `commands/` (кроме файлов, начинающихся с `_`). Роутер найдёт и загрузит её автоматически.

### Шаблон:
```python
from commands.base import BaseCommand, CommandResult

class MyFeatureCommand(BaseCommand):
    name = "my_feature"                    # Уникальное системное имя
    description = "Описание для справки"   # Обязательно (используется в команде help)
    category = "Моя категория"             # Группировка для справки
    keywords = ["фраза один", "фраза два"] # Что говорит пользователь
    priority = 8                           # 1-50, больше = проверяется раньше
    fuzzy_enabled = True                   # Искать ли с опечатками? (False для опасных команд)
    enabled = True                         # Можно временно выключить команду

    def extract_params(self, text: str, matched_keyword: str = "") -> dict:
        """(Опционально) Извлечь параметры из сказанного текста."""
        # text приходит уже очищенным от пунктуации в нижнем регистре
        cleaned = self._clean_text(text, self.keywords)
        return {"param": cleaned}

    def is_valid_candidate(self, params: dict) -> bool:
        """(Опционально) Вернуть False, если параметры невалидны (например, не найдено имя файла)."""
        return bool(params.get("param"))

    def execute(self, text: str, params: dict) -> CommandResult:
        """(Обязательно) Выполнить команду."""
        
        # 1. Сделать полезную работу
        my_param = params.get("param", "мир")
        print(f"Делаю работу с {my_param}")
        
        # 2. Озвучить результат
        self.speaker.say(f"Привет, {my_param}!")
        
        # 3. Вернуть результат. follow_up=True значит, что ассистент 
        #    продолжит слушать пользователя без wake word.
        return CommandResult(success=True, follow_up=True)
        
    def update_context(self, params: dict) -> None:
        """(Опционально) Обновить глобальный контекст для цепочки диалога."""
        from core.context import get_context
        get_context().update("my_feature", params.get("param"), params)

3. Соглашения по приоритетам (priority)
Роутер проверяет команды строго по убыванию приоритета.
Важное правило: если команда A содержит keyword, который является подстрокой keyword команды B — у A должен быть более низкий приоритет, чтобы B успела перехватить более длинную фразу.

50 — Максимальный (только для StopCommand)
16-20 — Контекстные операции (требуют знания предыдущей команды)
11-15 — Высокоприоритетные (опасные системные команды, макросы)
6-10 — Специфичные команды (погода, таймер, ютуб, громкость)
1-5 — Общие команды (могут перехватиться более специфичными)
-100 — LLM-фоллбэк (всегда проверяется последним, если ничего не подошло)
4. Как добавить интеграцию с новым сервисом
Если команда требует сложной логики взаимодействия с внешним миром (API, Win32, процессы):

Не пиши эту логику прямо в commands/.
Создай модуль в core/integrations/my_service.py.
Создай в нём класс или набор чистых функций.
Вызови эту интеграцию из команды в commands/my_service_cmd.py.
5. Доступные сервисы (AssistantContext)
В методе execute тебе доступен self.ctx (AssistantContext), который содержит:

self.ctx.speaker — для озвучки (say, beep).
self.ctx.config — для чтения config.yaml (get_str, get_int).
self.ctx.knowledge — база знаний (если включена).
self.ctx.recognizer — для запуска вложенных диалогов.
self.ctx.timer_manager — управление таймерами.
self.ctx.volume_control — управление громкостью.
self.ctx.weather_cache — кэш.
Не используй глобальные переменные (global) и не создавай новые синглтоны. Добавляй новые сервисы в AssistantContext (в main.py).

6. Опасные команды и подтверждения
Если команда делает что-то деструктивное (выключает ПК, удаляет файл):

Установи fuzzy_enabled = False.
Унаследуй её от _DangerousCommand (из commands/system.py).
Переопредели _do_execute() вместо execute().
Базовый класс сам спросит "Вы уверены?" и проверит ответ пользователя.

# Финальная проверка архитектуры

Мы завершили масштабное исследование и рефакторинг. Давай подведём итоги того, чего мы добились (сравнивая с целями из твоего первого сообщения):

1. **"Сколько файлов нужно изменить для интеграции с календарем?"**
   **Было:** ~5 файлов (включая модификацию ядра `router.py` и хардкод в `main.py`).
   **Стало:** 2 файла. Один для логики API (`core/integrations/calendar.py`), один для команды (`commands/calendar_cmd.py`). Роутер трогать больше не нужно (благодаря `update_context()`), контекст передаётся чисто.

2. **"Есть ли дублирование логики?"**
   **Было:** Огромное. Win32 API в 4 местах, алиасы приложений в 3 местах, парсинг согласий в 2 местах.
   **Стало:** Вычищено полностью. Win32 в `input_sim.py` и `window_utils.py`, алиасы в `UnifiedAppRegistry`, подтверждения в `BaseCommand`.

3. **"Не слишком ли много глобального состояния?"**
   **Было:** 13 синглтонов, большинство из которых не были потокобезопасны.
   **Стало:** Мы внедрили Dependency Injection. `timer_manager`, `weather_cache` и `volume_control` создаются в `main.py` и передаются через `AssistantContext`. Оставшиеся (контекст диалога) защищены `threading.Lock()`.

4. **"Оторванные от реальности тесты / сложность тестирования?"**
